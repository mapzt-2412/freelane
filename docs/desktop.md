# Experimental desktop manager

The header opens an existing VM configuration. A resizable, scrollable sidebar groups resources, lifecycle controls and guest app requests, while the main area is reserved for the display snapshot. The window supports a minimum size of 800 × 600; controls wrap within the sidebar.

The manager shows the configured acceleration: HVF requires Apple Silicon; TCG runs software emulation, with its selected threading mode shown separately from the guest CPU count. This describes configuration, not a hardware acceleration probe or a performance result.

Build both binaries from the repository root with `cargo build --locked --workspace`, then run `cargo run --locked -p freelane-desktop -- /absolute/path/to/vm.toml`. The desktop executable requires the `freelane` CLI next to it for Start, plus the QEMU/swtpm tools on PATH. Create the VM first using the CLI instructions in development.md. It does not rewrite configuration or initialize an existing disk.

Open VM validates and loads a canonical configuration path. Editing the textbox does not change the VM selected for controls until another file is opened. Only one operation runs at a time. Start launches the foreground CLI supervisor; errors are captured with a bounded buffer while stderr is drained continuously. Status is the most recent observation. Shutdown requests guest powerdown; check status for completion. Force stop discards guest RAM and may lose unsaved data.

Refresh display captures a PPM frame into a private temporary directory and decodes it with allocation/dimension limits. An optional checkbox refreshes the frame every five seconds. It defaults to off, uses the same single worker and decoding limits, and stops automatic refresh after a worker error. Automatic frames preserve app-request notices. Actual Linux GUI captures observed the guest firmware logo changing to a black boot frame without a manual Refresh click. Clicking a snapshot sends a primary mouse click using the USB tablet. The GUI maps the displayed image rectangle into bounded absolute coordinates; status must be running. Lost acknowledgment triggers only a best-effort release and reports uncertain delivery, without replaying a press. A failed click preserves the last observed VM status and its message while automatic frames can still show the effect. Actual Windows Terminal minimize/restore was observed through these GUI clicks. These are still snapshots, not continuous video or keyboard forwarding. Use the native QEMU window for keyboard input and interactive use; set runtime.headless=false on a machine with a display. Closing the manager leaves its VM running. Adopt an existing VM by opening its configuration in a new manager.

Linux verification used an authenticated Xvfb display, not a browser preview: actual Start/Pause/Resume actions changed QMP running state, closing the manager left the guest running, and the CLI subsequently stopped that test VM. A separate real Windows installer was displayed in the manager. macOS ARM64 cross-check passed, but linking, GUI execution and HVF still need a real Mac. No seamless app window or graphics acceleration is implemented.

The optional app controls use the same bounded guest-agent protocol as the CLI. Check guest connection sends ping. Launch app sends an absolute Windows .exe path or Ubuntu executable path and arguments as literal strings, with one argument per line, using no implicit shell. Buttons require guest_agent=true in the loaded configuration and a running agent in the guest (Windows also needs a compatible ARM64 serial driver). A process-start response does not verify the app window or its behavior. Requests are not automatically retried; a launch timeout leaves execution outcome unknown. The GUI timeout path was exercised against a real QEMU socket without an agent: it returned an error after the deadline, remained responsive, and kept VM status running. Successful GUI connection and launch were subsequently exercised over the real virtio driver in WinPE: it opened 7-Zip with a literal archive path containing spaces and an ampersand, and the correct window/file entry appeared. Installed Audit verification also observed GUI ping returning Windows/aarch64 and GUI Launch opening Notepad. Text was entered using diagnostic CLI keyboard controls, saved, closed and reopened via the real guest transport. Installed 7-Zip opened a persisted archive and its GUI Test reported no errors. Normal user sessions and native Mac validation remain separate gates.

## Settings and appearance

The blue/purple dark theme uses colored status text and a resizable controls sidebar. **VM settings** edits name, virtual CPU count, RAM in MiB, acceleration, TCG threading, NAT and network adapter, headless display, guest agent, UART console, installer image and read-only host folder. Firmware, TPM, guest disk and disk controller are preserved. Paths may be absolute or relative to the configuration directory. Clearing media/share paths detaches them on the next start.

Save creates a private backup beside `vm.toml`, validates the configuration/device plan and atomically replaces the file. TOML comments and formatting are retained in the backup, rather than in the rewritten file. The VM's runtime lock prevents saving while it is active, including when another manager started it. Changed on-disk text is rejected so the user can reopen it first. Changes take effect at the next start; device hot-plug is not implemented.

See [host file sharing](sharing.md) for the USB FAT limits and guest behavior. Physical GPU/USB passthrough and two-way folder synchronization are not implemented.

The GUI was exercised on authenticated Linux Xvfb: a disposable Ubuntu profile was opened, its name and host share path were changed through the settings form, Save was clicked, and the actual file and original backup were independently checked. The guest remained powered off for this UI check. The earlier responsive layout was also inspected at 1200 × 820 and 800 × 600. [Manager capture](assets/desktop-manager.png) and [settings capture](assets/desktop-settings.png) show the real GUI, not mockups. Native Mac GUI execution still requires hardware validation.

Validation for these settings/sharing changes passed 44 portable Rust tests, two real QEMU EFI media/profile tests with the shared USB volume, workspace build, format/Clippy and the macOS ARM64 desktop cross-check. The other four opt-in QEMU tests were not rerun for this change. Installed guest mounting and native Mac execution remain unverified.
